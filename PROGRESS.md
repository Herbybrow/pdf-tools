## Phase 13 — Sign PDF bug reports, Merge PDF rebuild, Scan to PDF editing + phone capture — **COMPLETE**

Continued user testing of Sign PDF surfaced two real bugs, fixed and precisely verified both:
- [x] **Cursor/drawing offset in the signature draw pad.** The canvas had a fixed pixel buffer (480×180) stretched wider via CSS (`w-full`) to fill its panel, but the mouse-position math never scaled for that difference — ink landed proportionally further right/down than the cursor the wider the panel actually was. Fixed by scaling `clientX/clientY` by `canvas.width/rect.width` (and the Y equivalent) before using them as drawing coordinates. Verified by drawing at a known screen position and reading back the canvas's actual pixel data: ink landed within 0.5px of the click (previously off by however much the panel exceeded 480px — confirmed stretched to 884px in the reproduction, a ~1.84× error).
- [x] **Signature could only be dragged within the page it started on.** Each page had its own `onMouseLeave` that cancelled the drag the instant the cursor crossed into the gap before the next page -- meaning it always cancelled at exactly the moment a cross-page drag would need to succeed. Rewired dragging to window-level `mousemove`/`mouseup` listeners that re-check which page's rect the cursor is over on every move, so it survives crossing page boundaries. Verified by dragging a signature from page 1 onto page 2: confirmed via `getBoundingClientRect()` that its final position falls fully inside page 2's bounds (not page 1's), and that it's still resizable/deletable there afterward.
- [x] Added pen size (thin/medium/thick) and a 4th colour (now black/red/blue/green, matching iLovePDF's own signature-modal palette from screenshots the user provided) to the Draw tab. - [x] **Scan to PDF: "Scan from your phone"** (QR code hand-off, matching iLovePDF's own scan flow from screenshots the user provided). Real-time relay: desktop shows a QR code and holds a WebSocket open; scanning it opens `/scan-mobile` on the phone, which uses `<input capture="environment">` to trigger the phone's native camera app (deliberately not `getUserMedia`, which requires a secure context a phone can't get talking to a LAN IP over plain HTTP); each captured photo POSTs to the backend and is relayed live to the desktop's WebSocket, landing in the exact same corner-adjustment review used for a local camera capture or file upload. No new backend PDF logic was needed — phone photos join the existing capture pipeline at the same point a file upload would.
  - Backend: `app/core/scan_sessions.py`, a small in-memory session manager (WebSocket set + page counter per session id), wired into the existing `organize` router (`/scan-session/{id}/ws`, `/scan-session/{id}/upload`) and the existing APScheduler for TTL cleanup of abandoned sessions — no images are ever written to disk.

  - This whole mode requires deliberately opting out of the local-only security posture (Section 4/Phase 10) for the duration of a scan session, since a phone is a different physical device and cannot reach `127.0.0.1` — documented explicitly in the README's new "Scanning from a phone" section, with exact steps, rather than silently loosening the secure default. Verified the full loop: found the machine's real LAN IP, ran temporary LAN-bound backend+frontend instances (never touching the user's normal 127.0.0.1-only servers' configuration), drove one Playwright browser tab as "desktop" and a second as "phone," confirmed the photo genuinely relays and reaches a downloadable, correctly-paginated PDF, then tore the temporary instances down and confirmed the normal secure servers still work and are still unreachable from the LAN afterward.

## Phase 15 — Real-use bug fixes, visual page pickers, Edit PDF property toolbar, watermark preview, homepage hero — **COMPLETE**

Another large voice-transcribed testing pass (with 10 iLovePDF comparison screenshots) surfaced a long list of concrete gaps and bugs across tools genuinely tested for the first time this phase. Everything below was found or confirmed via live testing against the real backend/frontend, not assumed from reading code -- several turned out to have a different root cause than the initial report suggested.

- [x] **OCR PDF was genuinely broken for Kiswahili and French** (not for English). Root-caused by directly hitting the endpoint with a synthetic scanned PDF: winget's Tesseract package only ships `eng`+`osd` language data, but the tool advertises `swa`/`fra`/`eng+swa` as selectable languages. Fixed by fetching the missing `.traineddata` files (plus Tesseract's `configs`/`tessconfigs`/`pdf.ttf` support files -- a tessdata dir needs all of these, not just the language files, or OCR fails with an unrelated-looking "Error occurred while parsing a Tesseract configuration file") into a new project-local `backend/tessdata/`, and pointing `TESSDATA_PREFIX` at it from `core/config.py` when present -- avoids needing admin rights to write into `C:\Program Files\Tesseract-OCR\`. `backend/scripts/install-deps.ps1` updated to provision this on a fresh machine. Verified all four language options end-to-end against a real scanned image with rendered text.
- [x] **PDF to Excel silently produced an empty file** for scanned/image-only PDFs, while iLovePDF at least told the user OCR was needed. Root-caused by reproducing with a real text-less scanned PDF: the existing text-dump fallback correctly found nothing (there was nothing to find), but returned a technically-valid, practically-empty spreadsheet instead of an error. Fixed: added an `ocrScanned` checkbox (mirroring PDF to Word's existing option) that OCRs the file before extraction, and a clear `ValueError` (surfaced as a real error message, not a blank success) when there's still no text after that. **Found and fixed a second, unrelated bug in the same investigation**: the borderless-table fallback strategy (which infers columns from text alignment) false-positives on ordinary paragraphs surprisingly often, shredding readable sentences into garbled single-word table cells instead of falling through to the plain-text dump -- fixed by only accepting a detected table if at least one row has 2+ columns. Verified against a real ruled table (unaffected), a scanned document without OCR (now a clear error), and the same document with OCR enabled (now clean full-line text instead of fragments).
- [x] **Compress PDF's "smallest" setting wasn't as small as it could be.** Ghostscript's canned `/screen` preset leaves real headroom on the table; added explicit per-tier image-downsampling resolution and JPEG-quality overrides (72dpi/JPEGQ 40 for smallest, 150/60 for recommended, 300/85 for best-quality) plus font subsetting and duplicate-image detection on top of every tier.
- [x] **PDF to PDF/A only offered 2 of the levels iLovePDF shows.** Added PDF/A-3b (Ghostscript genuinely supports part 3). Deliberately did *not* add the "a" (fully tagged/accessible) sub-levels some tools list, since Ghostscript's plain conversion can't actually guarantee accessibility tagging on an untagged source -- offering them would be a fake win, not a real one; a helper note now says so.
- [x] **The dual-pane preview pane looked "ugly"** -- it was the browser's own native PDF-plugin chrome (zoom/print/"Summarize" controls that don't belong to this app) embedded via `<iframe>`. Replaced with `DocumentPreview.tsx`: a custom canvas-rendered page view (pdf.js) with its own minimal dark chrome, a thumbnail rail for multi-page documents, and prev/next paging -- used by both the inline workspace pane and the fullscreen `PreviewModal`. Bonus: since it's canvas-based rather than the browser's opaque native viewer, it's now actually screenshot/inspection-testable, which the old iframe wasn't.
- [x] **PDF to Markdown had no Preview button at all** (and several other tools' previews were narrower than advertised). Root cause: `isPreviewableBlob` only recognized PDF/image MIME types.   - **Found and fixed a real, non-obvious selection bug while verifying this**: selecting any annotation shows the new properties bar, which shifts the whole canvas down a few dozen pixels.
